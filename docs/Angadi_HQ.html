Product Spec

Project Angadi — Telugu Square-like POS (Final Scope)

Locked 2026-10-19: single retail POS for kirana & pharmacy. Telugu UI · UPI + cash + udhaar · barcode scanner · Telugu voice billing · GST receipts · reports · inventory. No expiry module. No delivery module. Pharmacy = general retail (item library covers medicines).

One .NET MAUI codebase, ₹200/mo subscription. Architecture: Angadi_Architecture_Blueprint.md (canonical).

Positioning: "మీ అంగడి, మీ హిసాబు — మీ భాషలో." Your shop, your accounts, in your language.

1. The product — one retail POS (kirana + pharmacy)

Telugu Square-like POS. One vertical, general retail — the item library covers kirana goods and medicines alike:

  • Telugu-first UI — every label Telugu-first, English secondary; counter-sized touch targets, tablet-first landscape.
  • Telugu voice billing — "బియ్యం రెండు కేజీలు" → bill lines → confirm → tender. Voice mic also on item search.
  • Tenders — UPI (shop QR printed on receipt), cash, udhaar (dues ledger + WhatsApp reminders).
  • Barcode scanner — camera scan-to-add at counter and in item form (Item.Barcode, indexed); manual entry fallback.
  • Item library — categories, units, Telugu/English names + aliases, GST-inclusive price, GST slab, stock.
  • GST receipts — PDF with per-slab tax split, whole-rupee rounding line, UPI QR; WhatsApp share (free share sheet).
  • Inventory — per-sale stock decrement, low-stock alerts, StockMove audit trail.
  • Reports — day-end (tender split), GST summary, top items, udhaar outstanding.
  • AI integrated — on-device insights (reorder forecast, dead-stock radar, smart day summary; free) + capped LLM assistant (ask-your-data, supplier-bill scan; ≤50 calls/shop/mo, ~₹2–5/mo cost). Per blueprint §11.
  • Quick-sale grid + discounts — favourites grid; per-line and bill-level discounts.

2. Why this scope wins

  • One app, one paywall (₹200/mo), one Play listing, one Telugu reel channel — 3× cheaper to maintain than vertical sprawl.
  • Pharmacy needs no special module: medicines are just items with GST slabs. (Expiry tracking stays a v2 option, not v1 scope.)
  • Every feature above is proven by incumbents (Vyapar/myBillBook) — the wedge is Telugu-first + voice, which none of them do.

3. Domain — single vertical, no forks

Item (+ Barcode indexed), Bill, BillLine, Customer, StockMove, ShopProfile, Outbox, Meta. New interfaces vs the Galla contracts: IBarcodeScanner only. Everything else stands.

Design law: no per-shop-type forks in billing/inventory/dues logic — that's what keeps it maintainable without future agents.

Angadi — Architecture Blueprint (Software Architecture Document)

Final scope (locked 2026-10-19): Telugu-first Square-like POS for kirana & pharmacy retail. Telugu UI · UPI + cash (+ udhaar) · barcode scanner · Telugu voice billing · GST receipts · reports · inventory. No expiry module. No delivery module. Pharmacy = general retail vertical (item library covers medicines).

Stack: .NET MAUI · C# · Clean Architecture · on-device SQLite · zero backend · zero paid APIs in v1.

1. References — patterns stolen from the winners

Source Pattern stolen for Angadi
Khatabook (native Android-first, 10cr+ downloads) Offline-first as the default posture; observability is first-class even without a backend → our on-device log file + "Export logs".
Vyapar (offline-sync engine since 2019; WhatsApp deep links, not paid API) Offline is a per-task property, not a switch: billing/printing/stock/tender = no network; only future sync needs it. WhatsApp via unmetered tap-to-send deep links (wa.me), never the paid Business API in v1.
FloBiz/myBillBook (evaluated 6 months to build sync → chose Realm) The 6-month warning: design the ISyncService seam + Outbox pattern on Day 1, build the backend in v2. Every mutation writes local SQLite and an outbox row; the sync service drains it later.

SambaPOS 3 (OSS, C#) Ticket-based counter flow: ticket = bill draft, settle = tender. Our Bill lifecycle copies this.
Kahera POS (OSS, offline) Billing-math discipline: tax removed before discount, per-line deductions printed on the slip, one-tap end-of-shift report.
dotnet/eShop (Microsoft MAUI reference) Solution structure, DI composition, Shell navigation patterns.

2. Solution structure (monorepo, VS 2022)

Angadi.sln

├── Angadi.Voice           # Platform lib: ISpeechToText, Telugu parser, fuzzy matcher, te-IN resources
├── Angadi.Comms           # Platform lib: PDF renderer, WhatsApp share, Play Billing gate
├── Angadi.Domain          # Entities (zero dependencies)
├── Angadi.Application     # Mediator commands/queries/handlers, interfaces, pipeline behaviors

Reusability law (Rule of Three — satisfied: kirana, pharmacy, future apps): Core/Voice/Comms are versioned class libraries with AddAngadiVoice(services)-style DI extensions + Options pattern. v1 = monorepo project references; graduate to private NuGet feed when app #2 consumes them. [Obsolete] before any rename; SemVer.

3. Layers & dependency rule

Presentation (Angadi.Maui) → Application → Domain ← Infrastructure
  • Domain: entities, value objects, domain events (BillFinalized, StockAdjusted). Zero dependencies. GST-inclusive pricing invariant lives here.
  • Application: one command/query per use case as a record (FinalizeBillCommand, GetDaySalesQuery), handlers via Mediator (source-generator fork — no runtime reflection on mobile), pipeline behaviors: Validation → Logging → Transaction. Returns Result<T>; throws only for programmer errors.
  • Infrastructure: IUnitOfWork + IRepository<T> over sqlite-net-pcl (community standard; EF Core's startup/migration cost isn't justified for single-user on-device). Outbox writer. Android/iOS adapters (ISpeechToText, IBarcodeScanner, IReceiptShare).
  • Presentation: ViewModels only talk to IMediator. No INotifyPropertyChanged hand-written — CommunityToolkit.Mvvm [ObservableProperty]/[RelayCommand] source generators. Shell navigation, view-model-first, INavigationService for testability.

4. Data flow (the golden path: voice → paid bill)

Mic tap → VoiceViewModel → ISpeechToText.ListenAsync(te-IN)
  → stream partials → IVoiceBillingPipeline.ProcessUtteranceAsync
      → ITeluguParser → ParsedLine(name, qty, unit)
      → IItemMatcher (≥0.90 auto / 0.70–0.90 confirm / else no-match)
  → BillViewModel shows lines → tender → IMediator.Send(new FinalizeBillCommand)
      → ValidationBehavior → LoggingBehavior → TransactionBehavior
      → Handler: build Bill (GST-inclusive math, rounding) →
        repo.Save(Bill) + repo.AdjustStock (writes StockMove) +
        outbox.Append(BillFinalized) + dues.Update (if udhaar) →
        publish DomainEvent BillFinalized →
        handler chain: render PDF → queue WhatsApp share → UoW.Commit
  → UI: receipt screen (PDF preview, Share button, New Sale)

Rules: one transaction per command — a bill never half-saves. Expired batches can't exist (no expiry module) — but the StockBatch table is omitted entirely; if pharmacy needs it later, it's an additive migration. All user-facing strings from Telugu/English resources; errors from errors.json with correlation IDs.

5. Frontend — modern MAUI, Telugu-first

  • Toolkit trio (per Brandon Minnick NDC 2026): CommunityToolkit.Mvvm + CommunityToolkit.Maui + MAUI Markup (C# UI for dynamic counter screens, XAML for static forms).
  • Tablet-first landscape POS home: giant mic button with listening pulse, quick-sale grid, live bill panel, tender bar. Telugu-first labels, English secondary, large touch targets (counter gloves, noisy shop).
  • Design system: AngadiTheme resource dictionary — colors, type scale (Telugu script needs +15% line height vs Latin), spacing. No hardcoded colors/fonts in pages.
  • Barcode: IBarcodeScanner → camera via BarcodeScanning.Native.Maui (ZXing successor); scan-to-add on POS home and item form; Item.Barcode indexed lookup. Graceful fallback: type the code.
  • States everywhere: listening / no-match / no-internet-voice / empty / loading / error — each with Telugu guidance, never a dead screen.

6. Cross-cutting

  • Logging: MEL + Serilog file sink → /logs, 7-day rotation, 5 MB cap. Info: business events (bill finalized, scan, purchase). Warning: low-confidence matches, retries. Error: exceptions with correlation ID. Settings → Export logs (share file).
  • Errors: Result<T> at service boundaries; global handler in App.xaml.cs; errors.json (te/en), e.g. VOICE_NO_INTERNET: "వాయిస్ కోసం ఇంటర్నెట్ కావాలి — నొక్కి అమ్మండి".
  • Config: Options pattern (VoiceOptions, BillingOptions) bound from appsettings.json; shop profile from DB.
  • Validation: FluentValidation-style behaviors on commands (qty > 0, tender valid, customer exists for udhaar).

7. Data & the sync seam

  • Tables: Item (incl. Barcode indexed, TeluguName/EnglishName/Aliases JSON), Bill, BillLine, Customer, StockMove, Outbox, Meta. Seed: 80 kirana + 40 pharmacy items with Telugu aliases.
  • Outbox: (Id, AggregateType, AggregateId, PayloadJson, CreatedAt, SyncState). v1: append-only. v2: ISyncService drains with idempotent retry + tombstones (per the Starter Kit blueprint).
  • GST math: prices GST-inclusive (Indian MRP norm); TaxTotal = Grand − Grand/(1+slab); whole-rupee rounding with explicit RoundingAdjustment line.

8. Testing per layer

  • Domain: GST math, rounding, discount stacking (≥95% coverage — it's money).
  • Application: handler tests with in-memory repos; 30-phrase Telugu parser/matcher battery (target ≥27/30); pipeline confirmation thresholds.
  • Infrastructure: repo round-trips, outbox append, concurrent stock adjust (no lost updates).
  • UI: navigation smoke per screen; golden-path script (mic-simulated → tender → receipt) on 7" + 10" emulators.
  • System/UAT: 1 kirana owner + 1 chemist, 10 real bills each; defect log; FR-traceable test report.

9. Key ADRs (architecture decision records)

  1. sqlite-net-pcl over EF Core — single-user on-device; EF's migration/startup overhead unjustified (community standard; DevExpress template concurs).
  2. Mediator (source-gen) over MediatR — no runtime reflection cost on mobile; verify .NET 10 compat Day 1, fall back to MediatR if blocked.
  3. No backend in v1 — Outbox + ISyncService seam instead (FloBiz's 6-month lesson).
  4. WhatsApp via OS share sheet + wa.me deep links — ₹0 marginal cost (Vyapar/VoiceKhata pattern); Business API only if v2 needs automation, modeled as COGS.
  5. Telugu resources in JSON, never code — alias harvesting without recompiling logic.
  6. Monorepo project refs now, NuGet later — packing overhead only when app #2 exists.

11. AI integration — two tiers, margin-safe

Tier 1 — on-device intelligence (free, always on). No API, no cost, no internet needed. This is "AI" the shopkeeper feels daily: - Reorder forecast: "Rice 25kg will run out in ~6 days at current sale rate" — moving-average over sales history, per item. - Dead-stock radar: items with zero sales in 30/60/90 days, capital locked up. - Smart day summary: morning card — yesterday's sales vs average, top mover, dues to collect today. - Voice-matcher learning: every correction feeds the alias JSON (already in the pipeline) — the app gets smarter per shop, on-device.

Tier 2 — LLM features (capped, occasional, high value). Behind the AiFeatures flag, via IAiService: - Ask-your-data assistant: "last Diwali week sales?" / "which customer owes most?" — natural Telugu/English questions answered from local sales aggregates. - Supplier bill scan: photo of a distributor bill → extracted line items → one-tap stock-in. - Low-confidence voice rescue: when the fuzzy matcher scores 0.55–0.70, an LLM disambiguation call (with the shop's item list as context) instead of giving up.

The margin math (estimate): Tier 2 uses flash-class models at a fraction of a paisa per query. Even at 50 AI calls/shop/month, cost lands around ₹2–5 per shop per month — under 3% of the ₹170 net. The per-bill voice pipeline stays deterministic and free — AI never sits in the per-transaction hot path, so no bill ever costs you money.

Cost guardrails (non-negotiable): - Monthly per-shop AI call cap (default 50), meter visible in Settings; over-cap → Tier 1 only, with a Telugu notice. - All AI calls logged (count + tokens, never prompt PII) — you watch the spend per shop in the exported logs. - Provider swappable: IAiService with GeminiFlashProvider / OpenAiMiniProvider; switch by config, no code changes. Sai holds the API key; per-shop caps make the spend predictable.

Privacy: prompts carry aggregates and item names only — never customer names, phones, or full bills. Stated in the privacy policy.

Build placement: Angadi.AI platform library (joins Core/Voice/Comms). Tier 1 ships in v1; Tier 2 moves to v2 (SRS D2): an on-device app cannot hold an LLM API key safely, so v2 adds a small proxy that holds the key and enforces caps.

12. What this gives you in 5 years

A new vertical (say, the dhaba tracker) = new MAUI head + thin UI referencing Angadi.Core/Voice/Comms. No forked billing math, no duplicated GST logic, no second paywall to maintain. The platform compounds; the apps stay thin.

CROSS-CUTTING STANDARDS — Agent E sets up Days 2–3, everyone adopts

Logging (no paid services)

  • Result<T> pattern in Angadi.Application — no exceptions for expected failures (no voice match, timeout, no internet, duplicate item).

Idea source: the "Crore Idea" reel — a voice billing app where a Telugu kirana shopkeeper just speaks the items and the app makes the bill + updates stock. No typing, no English UI friction. Hindi has voice-khata apps; nobody owns Telugu voice billing. That lane is open.

1. Why this is the profitable pick
Customer price ₹99/month (₹999/year option). Undercuts myBillBook/Vyapar paid tiers; matches voice-app anchors (LekhaBook ₹149/mo, VoiceKhata ₹199/mo). Affordable for a kirana shop.
Your cut Google Play takes 15% → ~₹84 net per shop per month.
Your costs Play Console $25 one-time. No server, no database bills, no AI API bills (see §4). Domain ~₹1,000/yr optional. Claude Code $20 this month — already paid.

3. Architecture — enterprise-grade, opens in Visual Studio

.NET MAUI, Clean Architecture, MVVM. One solution, opens in Visual Studio 2022 — no exotic tooling, any .NET dev can maintain it after your Claude Code month ends.

Galla.sln
├── Galla.Domain            # Entities: Item, Bill, BillLine, Customer, StockMove… zero dependencies
├── Galla.Application       # Use cases, the voice-pipeline agents, DTOs, interfaces
├── Galla.Infrastructure    # SQLite (sqlite-net-pcl), PDF bills, Play Billing, file share
├── Galla.Maui             # UI (tablet-first layouts), ViewModels, platform speech adapters

Rules that keep it maintainable without future agents: - Domain never references UI or database — business logic stays pure and testable. - Every platform trick (speech, sharing, billing) hides behind an interface (ISpeechToText, IBillPrinter…) — swapping implementations never touches the UI. - Telugu language data (number words, units, item aliases) lives in JSON resource files, not code — you can fix a misheard word without recompiling logic.

4. The "multi-AI-agent" design — inside the app, at zero running cost

The app itself runs a 4-agent pipeline per bill. No LLM API calls — an LLM per bill would cost you money on every sale and destroy the margin. Instead, deterministic agents + on-device speech:

  1. Listener agent — captures audio, calls platform speech recognition (te-IN). Free (Google on Android).
  2. Parser agent — turns Telugu text into (item, quantity, unit): Telugu number words (ఒకటి, రెండు…), units (కేజీ, గ్రాములు, లీటరు), and quantity patterns — all from JSON rules you can extend.
  3. Matcher agent — fuzzy-matches heard names against the shop's item library + aliases ("బియ్యం" → Rice 1kg). Asks the shopkeeper to confirm on low confidence — this confirmation loop is the training data.
  4. Billing agent — prices lines, applies GST slabs + discounts, decrements stock, renders the PDF, queues the WhatsApp share.

Speech needs internet (Telugu recognition is cloud-backed) — the app must say so honestly instead of promising offline voice. Everything else works fully offline; bills queue and sync nothing (no server in v1).
